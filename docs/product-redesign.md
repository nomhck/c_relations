# C-Relations / Product redesign

## 今回の判断

目的はEPC工程の現在地を把握して、確認すべきタスクへ移動し、影響を理解したうえで編集できること。初回の中心を全ノードのキャンバスから、工程の見通し・重要工程・マイルストーンへ移した。CPM、グラフ検証、JSONフォーマット、MS Project交換、複数プロジェクトとIndexedDBは引き継ぐ。

- **概要 → 対象 → 編集**：指標・工種・重要タスクから対応するビューへ直接移動。
- **3つの読み方**：依存関係、ガントチャート、タスク一覧で同じデータを扱う。
- **必要なときに詳しく**：絞り込みは呼び出し式。詳細は基本情報・つながり・日程に分離。
- **変更前の判断**：所要日数を入力すると完了日への影響を試算し、明示的な適用後に更新する。
- **読みやすさ**：意味のある青・黄・緑・赤、十分な行高、日本語ラベル、本文と補足の階層、フォーカス表示、画面幅に応じた構成。
- **入口で操作を遮らない**：強制オンボーディングをなくし、担当部署は設定から変更する。

旧デザイン原則の「初期画面でフィルタを常時表示」から変更した理由は、利用者が絞り込み条件を決める前に、プロジェクトの現在地を理解できるようにするため。4,000タスクは引き続き集約・絞り込み・仮想化で扱う。

## データの意味

全体進捗はマイルストーンを除く所要日数による加重平均。重要工程は余裕日数0日以下かつ未完了のタスク。要確認は保留または日付制約超過。保存されたベースラインや実績日付がないため、遅延日数や予定対実績の比較は表示しない。表示日程は元のCPMの排他的終了日規約に従う。初回の21タスクは架空のサンプルと明示し、保存済みプロジェクトは置き換えない。

## 安定性

保存を直列化し、保存中の再編集、取り消しで復元したタスク、プロジェクト切替前の設定変更を失わないようにした。データ読込が完了してから編集を許可。ステータスと進捗の矛盾は新しい編集に対して正規化する。

取り込み時の全量保存も同じ保存処理で管理する。保存中に追加した保存ビューを失わず、全量保存に失敗した場合は次回も全量で再試行する。保存待ちの間に別のデータを取り込んだ場合も、最新の取り込みまで保存してから「保存済み」にする。

CPM計算では同じ暦日の日付変換を計算内で再利用し、祝日がない場合は祝日判定用の日付変換を省く。日付・休日・依存関係の計算規約は維持する。

## 検証範囲

単体テスト92件（既存74件、概要・編集整合性7件、保存11件）。4,000タスクでの表示導出とCPM性能の回帰検証を含む。TypeScriptと本番ビルドを実行。PR更新時とmain更新時にGitHub Actionsで単体テスト・型検証・GitHub Pages向けビルドを自動確認する。

CIでは性能テスト同士のCPU競合を避けるためテストファイルを直列実行する。既存の性能テストの合格基準は変更しない。

ブラウザの自動操作・スクリーンショット比較は今回未実施。既存E2Eの入口と変更された詳細画面のセレクタを更新し、新しい初回体験・工期プレビューのシナリオを追加したが、実行済みとは扱わない。

## 運用範囲

ブラウザ単位のローカル運用。共有編集・クラウドデータ同期・担当通知は含まない。JSONは従来の交換形式を維持する。MS Project XMLの担当・カレンダーの完全往復は元実装と同じ制約がある。利用者自身のバックアップはデータメニューから行う。
